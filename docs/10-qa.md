## 1. What this phase adds

Phase 6 made artefacts generatable; Phase 7 makes them **governable**. No
deliverable should reach a client because generation happened to succeed — it
reaches a client because a named, authenticated reviewer approved *that
version*, and every step in between is on an append-only trail.

Three capabilities:

1. **QA gate** — every deliverable carries a `qa_state`
   (`draft → in_review → approved | changes_requested → …`). Only
   `approved` is releasable; downloads of anything else are labelled
   internal copies in the UI.
2. **Revisions** — `POST /deliverables/{id}/revise` submits a new spec
   version: `spec_version` increments, the artefact regenerates under a
   versioned storage key, and **the QA gate resets** — a revised artefact is
   a new artefact and must earn approval again.
3. **Version history** — every successful build records an immutable row in
   `deliverable_versions` (exact spec, storage key, size, checksum, QA state
   at approval time). Superseded artefacts stay in storage and stay
   downloadable; history is never clobbered by a later build.

## 2. The QA state machine

```
            submit-review                approve (checklist, comment)
  draft ───────────────────▶ in_review ───────────────────────────▶ approved
    ▲                           │                                       │
    │        request_changes    │      checksum drift on regenerate     │
    └───────────────────────────┘◀────────────── (qa.reset) ────────────┘
    ▲                                   │
    └────── revise (new version) ───────┘ (any ready state)
```

- Transitions live in one matrix (`QA_DECISIONS` / `QA_ALLOWED_FROM` +
  the pure `qa_transition()` helper), unit-tested; illegal moves are honest
  409s, never silent overwrites.
- The **reviewer identity comes from the verified principal** — never the
  request body. In development that is the dev-anonymous principal; in
  production it is the Supabase `sub`.
- `request_changes` **requires a comment** (422 otherwise) — "changes
  requested" without a reason is not governable. The optional four-item
  checklist (figures verified · citations traceable · POPIA scan clear ·
  branding ok) is recorded with the decision as `qa_checks`.
- A QA decision updates the deliverable row **and the current version's
  record atomically**, so "which artefact version is approved" is a single
  queryable fact (`SELECT … FROM deliverable_versions WHERE qa_state='approved'`).

## 3. The checksum-drift rule

`POST /deliverables/{id}/regenerate` re-renders the current version
(`force` bypasses the handler's ready-skip). Because builders are
deterministic, a healthy re-render produces **byte-identical output —
the checksum comparison in the ready event proves it**, and QA approval
survives. If the checksum ever differs (e.g. a builder upgrade changed the
output), the approval is **voided automatically**: `qa_state → draft` with a
`qa.reset` trail event naming both checksums. Approved artefacts can never
silently change under their approval.

## 4. Versioned storage

Keys now carry the artefact version — `…/deliverables/{id}.v{n}.{ext}` — so
a revision never overwrites a superseded artefact. The version row records
the exact spec that produced the bytes (auditable reproduction), the
checksum, and the QA state the version shipped under. `GET
/deliverables/{id}/versions` lists them newest-first.

## 5. API surface (Phase 7 additions)

```
POST /deliverables/{id}/submit-review   ready + draft|changes_requested → in_review
POST /deliverables/{id}/qa              in_review → approved | changes_requested
POST /deliverables/{id}/revise          new spec version → queued, gate reset (202)
POST /deliverables/{id}/regenerate      re-render current version (202)
GET  /deliverables/{id}/versions        immutable per-version records
```

All guarded by 409 state rules, 422 validation rules, and TV-012 isolation
(cross-org → 404). The list endpoint now carries `spec_version`, `qa_state`
and `qa_reviewer`.

## 6. Frontend

The Deliverables view gains a **QA column** (state pill + version chip), the
state-appropriate action buttons (Submit · Approve · Changes · Revise), a
**QA decision modal** (checklist + comment, reviewer from session), a
**version-history modal**, revise mode in the builder modal (spec prefilled,
format/scope frozen, revision note goes on the trail), and the honest
download toast: unapproved artefacts download as **"(internal copy)"** with
an explicit not-QA-approved notice. Demo mode shows all four QA states and
guards every action.

## 8. Deliberately not in this phase

- **Per-release approval (named recipient lists)** — the master spec ties
  release registers to the client portal (Phase 8 internal ops); the QA gate
  here is the prerequisite, not the register.
- **Two-reviewer rule** — the master spec's ADR set makes the POPIA gate
  (ADR-014) the hard control; a four-eyes rule on QA is a one-line addition
  to the transition matrix when the company wants it.
- **PPTX/branding templates** — unchanged from CAIOS-DEL-001 §8 (TV-024).
